Three systems, and the measurements behind them.

The handwriting engine that writes maths as pen strokes, the visualisation cascade that refuses to draw a wrong diagram, and the learner profile that models a student against their own baseline. Every number on this page comes from an instrumented run on a physical iPad, including the ones that went the wrong way.

The handwriting system

The tutor's answer has to arrive as ink on the student's own canvas: erasable, selectable, at the same zoom, in the same coordinate space. That rules out rendering text and rules out playing a video. It has to be strokes, composed at run time.

Why the stages split where they do

Each stage emits a different kind of thing, and that is the whole reason the split exists. The layout engine emits geometry and is forbidden from touching ink properties. The composer applies personality and never moves a glyph. The scheduler owns timing and nothing else.

That last one was a refactor, not the original design. The animator used to inline its own duration and pause arithmetic, which meant the live render, the debug overlay and the tests could each compute a slightly different timeline. Pulling the schedule out into one pure function made the three agree by construction.

Determinism, and the one exception

The schedule is a pure function of stroke metadata, line breaks and tuning. The only stochastic element is the noise on inter-stroke pauses. Everything else is seeded, so the same string renders identically twice and a test can assert the timeline rather than a human judging a screenshot.

What the composer does per stroke

  1. Control points

    From the glyph polyline or a primitive shape.

  2. Jitter

    Small per-point displacement, scaled by the style profile.

  3. Baseline drift

    y shifts as a function of global x, so a long line sags the way a real one does.

  4. Slant

    A horizontal shear around the expression's baseline, not the glyph's own. That is what makes a numerator and its denominator share one slant instead of leaning independently.

  5. Densify and pack

    Resample to a maximum point spacing, then pack into PKStrokePoints with width, force and opacity from the profile.

Three generations, on purpose

There is an older CALayer text-mask engine, a glyph-stamp engine, and the AST pipeline above. The glyph-stamp engine is still shipped, because it is the fallback: if the parser or the layout engine refuses a string, the render falls through to it rather than to nothing. A tutor that silently writes nothing is a worse failure than a tutor whose handwriting is a generation behind.

The aesthetic target is deliberately narrow: a calm, deliberate, premium hand. Not shaky, not artistic, not over-humanised. Every constant that controls it is live-tunable in an in-app lab, and the lab's defaults match the baked constants byte for byte, so having the lab available does not change what production renders.

The visual engine

When a diagram would help, Klera generates an interactive one. The hard part is not generating it. The hard part is refusing to show one that is wrong, because a confidently wrong diagram teaches a student something false.

The model recommends, the engine decides

The model may ask for a 3D render on anything. The router grants it only when the third spatial dimension earns its place: a surface, a plane in three-space, a cross product, a volume. A parabola drawn as a ribbon in space is worse than a parabola, so a topic that reads as standard 2D falls back to the flat cascade even when the model asked for depth.

The gate has two halves

The static half scans generated code for escape hatches and rejects it before it reaches a web view. That sits on top of a content security policy that already blocks the network, which is defence in depth rather than belt and braces: the AI supplies parameter values, so a template must never become an injection vector.

The dynamic half renders the widget once off-screen and requires it to clear instrumentation minimums. A widget that renders but does nothing, for instance a JSXGraph board that is only a slider, is refused too.

The bottom tier cannot fail

Tier 3 is deterministic, local, and never invents mathematics. It has three moves, in order:

  1. Nearest curated template

    With the problem's own parameters if they validate.

  2. The template's example parameters

    Clearly labelled a general example, never passed off as this student's problem.

  3. A retry card

    Unknown topic, so it shows the problem text back and offers a fresh generation. No made-up numbers, no fake graph.

The whole sandbox, JSXGraph and KaTeX included, is served from the app bundle over file://. Instant, offline, no network dependency at the moment a student is waiting.

Why per-student, and not a population threshold

The obvious design is a fixed threshold: this much pressure means stress, this much jerk means struggle. We built per-student baselines because the theory said population thresholds would not transfer. Two device runs turned that from theory into evidence, and the evidence was stronger than the theory.

What separates student B is a different channel entirely: the pause before they start writing.

So the finding is sharper than "students differ in scale". The direction and the channel of distress differ per student. Student A's only separator is student B's flattest signal, and the reverse. That is an argument for per-student baselines that no amount of tuning a global constant can answer.

The maths, exactly as it runs

dysfluency = sigmoid( 0.7 · zJerk + 0.5 · max(0, −zSpeed) − 1.0 ) Jerky strokes push it up. So does writing unusually slowly, but only in the slow direction, which is why the speed term is one-sided. The −1.0 offset means an unremarkable sample lands at sigmoid(−1.0) = 0.27, not at 0.5.
strain = sigmoid( 0.8 · zForce − 1.0 ) · paired paired is 1.0 when the attempt is known not to have progressed, or shows two or more erase bursts, and 0.3 otherwise. Pressing hard on work that is going fine is not strain; pressing hard on work that is going nowhere is.

The bug that taught us the most

paired used to take the full 1.0 whenever the attempt's outcome was unknown, because "not known to have progressed" was being read as "did not progress". Those are not the same claim. An outcome is unknown when our background verifier did not get round to judging the work, which is a fact about our compute budget, not about the student.

The cost was measurable. One run posted its highest strain reading of the whole session, 0.51, on a calm attempt with zero erasures, purely because nothing had marked it yet. That is the app inventing a struggling student out of its own queue depth.

The fix makes progress three-state. Abandonment is the only outcome that pairs as no-progress; absence of evidence takes the unpaired weight. The same mistake was found in two other places in the codebase once we knew its shape.

An estimator can talk over the student

The baseline is a running robust centre and median absolute deviation, advanced by an exponentially weighted average at alpha = 0.05. Seeded on the first sample, its accumulated weight after twelve observations is only 0.46. The centre had travelled less than half way to the true mean, and the deviation was under-converged by the same factor.

That is not an abstract concern. The first clean sample of one run happened to be the session's smoothest writing, so the centre stayed anchored near it and every post-baseline jerk z-score came back positive.

The arithmetic closed exactly, which is how we knew it was the estimator and not the student. A biased zJerk = +1.10 gives sigmoid(0.7 · 1.10 − 1.0) = 0.44, and the log said 0.45. At an unbiased zJerk = 0 the same formula gives 0.27. Calm, unaided, seven-second work had been sitting at 64 percent of its threshold for no reason at all.

The row we will not tune away

Attempt 24 was calm. No erasures, no negative language, solved. It read dysfluency 0.57, zJerk +1.86, zSpeed +2.30. Attempt 23, genuinely stuck, read 0.56.

Fast confident writing and stuck writing are indistinguishable on this student's dysfluency channel. Any proposal to lower the 0.70 threshold toward these values fires on confident work, which is the worst possible false positive: interrupting a student who is doing well. The threshold stays where it is until there is data that justifies moving it, and a threshold sweep on the four struggle rows we have across two students would be fitting to noise.

The open defect, stated plainly

Every one of those twenty-six attempts finalised with outcome=unknown and difficulty=unknown, while the background verifier was demonstrably working and judging correctly at full confidence. The verdict lands and credits mastery; it just never reaches the attempt record.

That cascades exactly one way:

verdict does not attach → difficulty stays nil → pace baseline is never fed → pause detector returns none on every attempt

Which means the signal that separates this student by a factor of eleven is the one signal structurally unable to fire. Two previously separate bookkeeping items in our tracker turned out to be the same defect, hiding the same thing.

A note for anyone chasing it: comparing the attempt's cluster hash against the verify hash proves nothing. The attempt's hash is set once at the first stroke and never reassigned, while the verify hash is a digest of the mature cluster. They are different by construction and will never match. We went down that path first.

Three things that will cost you a session each

Attempts bank on shrink, not on finish

Pruning folds only clusters at or beyond the current count, and it is driven by the cluster count changing. Writing more problems raises the count and prunes nothing, so attempts stay open indefinitely while the verifier keeps judging them and crediting mastery. The app looks completely alive with the observation count frozen. One run sat at 11 of 12 through a dozen problems for exactly this reason.

Zero by construction is not calm

Before the baseline gate opens at twelve clean samples, every dysfluency and strain figure is zero because nothing can be computed, not because the student is relaxed. Reading a low value as calm before the header says the baseline is ready is reading the absence of a measurement as a measurement.

A tiny attempt is garbage, not data

A three-stroke probe produced a raw speed two to three times anything else in the run. An earlier run let a sample like that through and got a z-score of +10.73. The guard now rejects anything under five strokes or five active seconds and returns nil, so a discarded sample adds no support rather than removing any, and it does not pollute the baseline either.

What we are not claiming

Four struggle attempts across two students is not a dataset. We cannot run a threshold sweep on it and we have not tried. One of our two students shows jerk z-scores that are eight of nine negative, which is plausibly real within-session smoothing rather than residual estimator bias, and one session cannot separate the two. The keyword list that scores a student's own words has a documented inversion, where "idk how to solve this" scored as a constructive question because the constructive list matched inside it. The language model read the same sentence as confusion at 0.90 confidence on the next log line.

All of that is on this page because a page that showed only the parts that worked would tell you nothing about whether the parts that worked are real.
